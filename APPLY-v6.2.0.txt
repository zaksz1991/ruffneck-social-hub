RUFFNECK SOCIAL HUB v6.2.0 — APPLY INSTRUCTIONS
Flutterwave billing operations, webhook visibility and manual approval hardening

BASELINE
This patch targets RuffNeck Social Hub v6.1.3 on the main branch, including the v6.1.2 Public-Key/manual-review integration and v6.1.3 billing review console. Do not apply over a different billing implementation or an older branch.

GITHUB FILES

2. Add the two new files:

   - scripts/test-flutterwave-operations.mjs

5. Commit the files to main through GitHub's web interface. Inspect the resulting Vercel deployment log.

WHAT CHANGES
- Reworks the Flutterwave setup page status wording so a present key/hash is not described as proof of an active merchant connection.
- Adds a read-only webhook activity panel using the existing server-side billing_webhook_events journal: authenticated event count for 24 hours, processing failures, retryable/incomplete events and the latest six event outcomes.
- Displays only event type, outcome and timestamps. It does not expose transaction/customer data, secret hashes or service-role credentials.
- Tightens the payment-plan ID field to the numeric, JavaScript-safe range accepted by the server.
- Requires a platform billing administrator to tick the provider-dashboard attestation, type APPROVE exactly and enter a 20–2,000 character review note containing the exact transaction ID before the approval server action can call the protected database function.
- Replaces the billing subscription audit's brittle regex-source-text check with executable runtime checks for both standard and explicitly tagged V3 Live Public Key formats. This prevents equivalent regex spellings from breaking the build again.

SUPABASE
No SQL migration is required. The feature reads the existing billing_webhook_events table from migration 0043 and preserves the protected payment-review table/function from migration 0047. Do not re-run earlier migrations.

VERCEL / FLUTTERWAVE
- No new environment variables are required.
- Keep NEXT_PUBLIC_FLW_PUBLIC_KEY and FLW_SECRET_HASH as already configured.
- Keep the Supabase service-role key server-side only.
- This release does not require or invent FLW_SECRET_KEY.
- The webhook activity panel is passive: it reports events RuffNeck has received after the verif-hash check. It cannot prove Flutterwave is configured to send every notification and cannot generate a provider-side test event.

PAYMENT SAFETY
A webhook hash authenticates the sender; it does not verify the charge. Customer redirects and webhook events still do not activate subscriptions. The platform administrator must independently compare the transaction ID, successful status, amount, currency, customer email, transaction reference and payment-plan ID in Flutterwave Dashboard. Only then should the transaction be approved in RuffNeck. The new typed phrase and audit note make accidental approval harder; they do not replace provider verification.
