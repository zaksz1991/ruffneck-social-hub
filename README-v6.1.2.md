# RuffNeck Social Hub v6.1.2 — Flutterwave V3 Public-Key Checkout

## Purpose

This release makes use of the Flutterwave V3 Live Public Key that the merchant already has. It adds a limited checkout path that does **not** require a V3 Live Secret Key to open Flutterwave Inline checkout.

Because Flutterwave's server-side transaction-verification endpoint requires the Secret Key, this release deliberately does **not** activate subscriptions from a browser redirect or webhook alone. A successful `charge.completed` webhook is authenticated with the merchant-configured webhook Secret Hash, recorded, and placed in an administrator review queue. A platform billing administrator must independently inspect the transaction in the Flutterwave merchant dashboard and approve it inside RuffNeck before an initial subscription is activated or a renewal extends the billing period.

This is an interim, manual-verification operating mode. It is not equivalent to fully automated payment verification.

## What changed

- V3 Flutterwave Inline checkout uses `NEXT_PUBLIC_FLW_PUBLIC_KEY`.
- The server creates the transaction reference and pending RuffNeck invoice through the existing authenticated, workspace-owner/admin-only Supabase RPC.
- Checkout passes the manually configured environment-specific `payment_plan` ID, amount, currency, email, reference and return URL to Flutterwave Inline.
- Test and Live Public Keys are detected by their prefixes. Test and Live payment-plan IDs remain stored separately in `billing_plans` through migration 0046.
- The customer return route is informational only. It never activates a subscription.
- The V3 webhook validates `verif-hash` using `FLW_SECRET_HASH` and uses constant-time comparison.
- Successful charge notifications are matched to a pending invoice by transaction reference, or to one unambiguous active/past-due subscription for a recurring payment. They are added to a protected manual review queue.
- Failed charge notifications are logged only in this mode; they do not automatically change subscription access.
- The administrator review action is protected by `BILLING_PLATFORM_ADMIN_EMAILS` and a service-role-only database function. The administrator must confirm the provider dashboard details and enter a review note before approval.
- Payment-plan IDs are entered after the administrator creates and inspects the plans in Flutterwave Dashboard. RuffNeck records the administrator's confirmation but does not claim to verify the plan through the API.
- Existing campaign, CRM, inbox, agency-client and entitlement pages are retained. The billing page retains the usage link and managed-client allowance disclosure.

## What this mode cannot do

Without the V3 Live Secret Key, RuffNeck cannot:

- call the authenticated V3 transaction-verification endpoint;
- create or query payment plans through Flutterwave's API;
- automatically verify the full transaction record;
- automatically activate or renew paid access from a webhook;
- automatically reconcile payments when a webhook was never delivered.

Every successful initial payment and recurring renewal needs a manual check in Flutterwave Dashboard before the subscription status is changed in RuffNeck. Notifications that cannot be matched to one pending invoice or one unique subscription are marked `needs_attention` and cannot be approved through the normal queue action.

- `0046_flutterwave_environment_plan_ids.sql`

It also preserves the current entitlement/agency billing UI and expects the already-used migrations 0044 and 0045 to remain applied when those modules are in the deployed project. Apply the new migration only after migration 0046:

## Vercel environment variables

Configure these in Vercel → RuffNeck Social Hub → Settings → Environment Variables. Use the Production environment for Live checkout.

| Variable | Value | Exposure |
|---|---|---|
| `NEXT_PUBLIC_FLW_PUBLIC_KEY` | The full V3 Live Public Key beginning `FLWPUBK_LIVE-` | Public key; safe for browser checkout |
| `FLW_SECRET_HASH` | A strong random string generated by the merchant | Secret; server-only |
| `NEXT_PUBLIC_APP_URL` | `https://ruffneck-social-hub.vercel.app` | Public URL; if it is absent, the app also accepts the already-configured `NEXT_PUBLIC_SITE_URL` or Vercel deployment URL |
| `BILLING_PLATFORM_ADMIN_EMAILS` | Comma-separated RuffNeck platform administrator email address(es) | Server-only |
| `SUPABASE_SERVICE_ROLE_KEY` | Keep the existing server-side Supabase service-role key | Secret; server-only |

Keep the existing Supabase URL and anon key. Do not expose the service-role key in a `NEXT_PUBLIC_` variable or commit it to GitHub. Do not put the Live Public Key into `FLW_SECRET_KEY`. This interim implementation does not require `FLW_SECRET_KEY` and does not use Flutterwave V4 credentials.

The project already has `NEXT_PUBLIC_SITE_URL` configured in some deployments; the v6.1.2 code accepts that as a fallback, so you do not need to create a duplicate URL variable when it already points to the production domain.

For Preview/Test deployments, use a separate Test Public Key beginning `FLWPUBK_TEST-`, a Test webhook configuration, and Test plan IDs. Never mix Test and Live keys or plan IDs.

## Flutterwave Live webhook configuration

In Flutterwave Dashboard → Settings → Webhooks → Live:

- URL: `https://ruffneck-social-hub.vercel.app/api/webhooks/flutterwave`
- Secret hash: the exact same value stored as `FLW_SECRET_HASH` in Vercel
- Enable V3 webhooks
- Enable webhook retries
- Enable resend webhook from the dashboard
- JSON response format may be enabled

The webhook endpoint only accepts a request when the `verif-hash` header matches the configured secret hash. A correct webhook signature authenticates the sender; it does not replace transaction verification. This is why the endpoint queues successful payments instead of granting access automatically.

## Create and map Live payment plans

1. Open Flutterwave Dashboard → Payments → Payment Plans.
2. Create each paid plan with the same amount, currency and interval displayed in RuffNeck's `/platform/billing-setup` page.
3. Check the plan carefully before saving its ID. The current catalogue seed uses NGN 5,000 monthly (Starter), NGN 15,000 monthly (Professional), and NGN 40,000 monthly (Agency); these are the values currently stored in the database, not a statement that prices have been commercially approved. Review prices before creating live plans.
4. Unless a fixed number of cycles is intended, configure the plan without a duration so Flutterwave continues recurring billing until cancellation.
5. Copy the numeric Payment Plan ID from the Flutterwave dashboard.
6. Open `https://ruffneck-social-hub.vercel.app/platform/billing-setup` as an authorised platform billing administrator.
7. Enter the ID on the matching RuffNeck plan card, confirm that its amount/currency/interval exactly match the provider plan, and save.

Saving a plan ID does not make a charge and does not query Flutterwave. The administrator's confirmation is recorded as a manual attestation. If a plan price, currency or interval is later changed in Supabase, migration 0046 clears its stored Test and Live plan IDs and disables those mappings until they are reviewed again.

## Customer checkout flow

1. A signed-in workspace owner/admin opens `/billing` for the correct workspace.
2. They select an available paid plan. RuffNeck checks the logged-in user's workspace role and reserves one pending invoice on the server.
3. The browser loads Flutterwave V3 Inline with the Public Key, server-generated transaction reference, amount, currency, customer email and mapped Payment Plan ID.
4. Flutterwave collects the payment details. RuffNeck does not store card number or CVV data.
5. The browser is redirected to `/api/billing/flutterwave/callback`. That route treats all query parameters as untrusted and displays a pending-review notice only; it does not activate the subscription.
6. Flutterwave sends the V3 webhook to `/api/webhooks/flutterwave`. RuffNeck authenticates `verif-hash`, deduplicates the event, and queues a successful transaction for manual review.
7. The platform billing administrator opens `/platform/billing-review`, then independently finds the transaction in Flutterwave Dashboard → Transactions.
8. The administrator checks the transaction ID, successful status, amount, currency, customer email, transaction reference and Payment Plan ID against the queued record and RuffNeck invoice.
9. Only after all details match does the administrator tick the confirmation box, enter a review note of at least 20 characters and approve. The protected Supabase function activates the first subscription or records the recurring renewal.

Do not approve a browser redirect or webhook payload by itself. Leave mismatched or ambiguous records in `needs_attention` and investigate them in the Flutterwave dashboard.

## Operational cautions

- An abandoned checkout leaves a pending invoice until its status is reconciled. Do not create another payment for that workspace while the invoice remains pending.
- If a successful payment was taken but the webhook was not delivered, the payment will not automatically appear in the review queue. Inspect it in Flutterwave Dashboard and use the existing support/reconciliation process; do not tell the customer that RuffNeck has automatically activated access.
- Successful recurring charges also require manual review before the billing period is extended in RuffNeck.
- A webhook with ambiguous workspace/subscription matching is not eligible for approval from the normal queue action.
- This package does not connect to the merchant's Vercel or Flutterwave accounts. The merchant must configure their own environment variables and webhook settings.
