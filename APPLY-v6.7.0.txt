RUFFNECK SOCIAL HUB v6.7.0 — CONSOLIDATED INSTALLATION
Workspace billing history, subscription lifecycle and daily processor

BASELINE
This consolidated overlay is aligned to the v6.4.0 deployment log at commit b4dc17f. It carries forward the v6.5.0 subscription lifecycle controls and v6.6.0 daily lifecycle processor, then adds v6.7.0 workspace billing history. It is not a full repository export. Do not replace the entire GitHub repository with the ZIP.

1. GITHUB FILES
Extract the ZIP. Add the files marked NEW and replace the files marked REPLACED in PATCH-MANIFEST-v6.7.0.txt at their exact repository paths. The package.json is release 6.7.0 and contains the existing v6.4 billing checks plus the v6.5/v6.6 lifecycle checks and new v6.7 billing-history checks. Preserve any custom npm scripts not represented in this package by merging them.

If GitHub main is already on v6.5.0 or v6.6.0, this consolidated package is a superseding set of those billing files; it can still be used, but compare custom changes before replacing files.

2. SUPABASE MIGRATIONS — CHECK HISTORY FIRST
The package includes migrations 0048, 0049 and 0050. In Supabase migration history, check each one separately. Apply only those that are missing, in this order:
- 0048_flutterwave_missing_webhook_reconciliation.sql
- 0049_subscription_lifecycle_management.sql
- 0050_daily_subscription_lifecycle_processor.sql

Migration 0048 was already included in the v6.4.0 package. Do not re-run any migration that has already succeeded. Migration 0049 creates subscription lifecycle events and guarded lifecycle actions. Migration 0050 adds the daily processor run journal and protected batch function. v6.7.0 adds no new migration.

Standalone SQL files are included in the separate `ruffneck-v6.7.0-migrations-0048-0050.zip` and are also provided as .txt copies. Open the .txt version if your system does not open .sql files directly, copy the entire contents, and paste into a new Supabase SQL Editor query.

3. VERCEL ENVIRONMENT
The v6.6.0 daily processor requires a server-only `CRON_SECRET` in both Preview and Production. Use a strong random value of at least 32 characters, distinct from `FLW_SECRET_HASH`. Never use a NEXT_PUBLIC_ prefix and never commit the value to GitHub. Redeploy after saving the variable. Keep the Supabase service-role key server-side only. No Flutterwave Secret Key is invented or required by this public-key/manual-review flow.

4. VERCEL CRON CONFIGURATION
The carried-forward `vercel.json` schedules `/api/cron/subscription-lifecycle` daily at `03:00 UTC`. On Vercel Hobby, invocation timing is distributed within the configured hour. If GitHub main already contains a `vercel.json`, merge only the `0 3 * * *` cron entry into its existing `crons` array; do not overwrite other project configuration. Confirm the schedule appears in Vercel → Project → Settings → Cron Jobs after deployment.

5. NEW WORKSPACE BILLING HISTORY
After deployment, signed-in workspace owners/admins can open `/billing/history`. It shows recent Flutterwave payment-review records and subscription lifecycle event labels for workspaces where the signed-in user currently has owner/admin billing membership. Filters include 30/90/365 days and payment review status. The page provides a CSV statement export.

The page and export re-check workspace membership server-side. They omit customer email, card data, payment/reconciliation notes, lifecycle event notes, actor IDs and internal event metadata. Only records with `review_status=approved` and `provider_status=successful` have completed the separate administrator review. Pending and needs-attention notifications are not collected funds.

6. PAYMENT AND LIFECYCLE SAFEGUARDS
- Browser redirects and webhook receipts do not activate subscriptions by themselves.
- Successful initial payments and renewals still require the existing platform-admin manual approval in Flutterwave Dashboard.
- Workspace cancellation requests do not cancel a recurring Flutterwave plan. An administrator must cancel it in the provider dashboard and separately confirm the action in RuffNeck.
- Daily cron only marks overdue active subscriptions past due and finalizes cancellations whose provider cancellation was already confirmed and whose paid term ended. It does not verify payments, contact Flutterwave, approve reviews, expire grace-ended subscriptions or cancel provider plans.

7. VALIDATION
Focused v6.5/v6.6 billing regression tests and new v6.7 unit/integration checks are included. Full repository `npm test`, full Next.js production build, remote Supabase migrations, real Vercel Cron execution, and live Flutterwave transactions must still be verified against the actual deployment. Do not treat focused tests as proof of a successful production deploy.
